# Пример демонстрации балансировки нагрузки

## Сценарий использования: Балансировка нагрузки в микросервисной архитектуре

Представим, что у нас есть система микросервисов с разной нагрузкой. Давайте рассмотрим пример:

### Система:
- Сервис "user-service" - обслуживает пользовательские запросы
- Сервис "order-service" - обрабатывает заказы
- Сервис "payment-service" - обрабатывает платежи

### Пример данных нагрузки:

```

2023-10-01 00:50:00  120
2023-10-01 00:55:00  140
```

### Прогнозирование и масштабирование:

1. **Начальное состояние**: 
   - user-service: 2 реплики
   - target_per_replica = 30 requests/sec

2. **Прогноз нагрузки на следующие 5 минут**:
   - Прогнозируем, что нагрузка будет расти до 160 requests/sec
   - Требуемое количество реплик: ceil(160/30) = 6 реплик

3. **Учет асимметричной коррекции риска**:
   - Если мы недооценим нагрузку, это может привести к отказам (SLA violation)
   - Альфа-коэффициент (lambda_plus = 0.5) обеспечивает быструю реакцию на недооценку
   - Итоговый прогноз будет выше обычного из-за "безопасной" поправки

4. **Решение о масштабировании**:
   - Текущие реплики: 2
   - Необходимые реплики: 6
   - Максимальный шаг масштабирования вверх: 2 (scale_up_step_limit)
   - Следующее количество реплик: 4

5. **Применение изменений**:
   - Kubernetes API вызывает изменение с 2 до 4 реплик
   - Запускаются новые поды для обработки увеличивающейся нагрузки

### Влияние на балансировку:

1. **Горизонтальный масштабинг**:
   - Увеличиваем количество реплик для обработки большего объема запросов
   - Распределяем нагрузку между более большим количеством экземпляров

2. **Адаптивность к трендам**:
   - При линейном росте нагрузки система предвидит этот рост и масштабируется заранее
   - Снижается вероятность перегрузки сервиса

3. **Контроль изменений**:
   - Ограничения на шаг масштабирования предотвращают резкие изменения
   - Cooldown-периоды защищают от "дребезга"

### Преимущества системы:

1. **Раннее реагирование**: 
   - Масштабирование происходит до достижения критического уровня нагрузки
   - Повышается надежность сервиса

2. **Оптимизация ресурсов**:
   - Не перегружаем систему лишними репликами
   - Уменьшаем избыточное потребление ресурсов

3. **Адаптация к изменяющимся условиям**:
   - Асинхронная коррекция риска позволяет адаптироваться к различным типам нагрузки
   - Обеспечивает гибкость в настройке параметров для разных сервисов

### Пример конфигурации:

```yaml
# config.yaml
prometheus_url: "http://prometheus:9090"
services:
  - name: "user-service"
    promql: "rate(http_requests_total{service='user-service'}[5m])"
    target_per_replica: 30
    min_replicas: 1
    max_replicas: 10
    scale_up_step_limit: 2
    scale_down_step_limit: 1
    cooldown_seconds: 60
```

### Как система балансирует нагрузку:

В рамках предиктивного автоскейлинга, балансировка нагрузки происходит следующим образом:

1. **Прогнозирование**:
   - Модуль forecaster использует алгоритм ARAF (Asymmetric Risk-Adaptive Forecasting) для прогнозирования будущей нагрузки
   - Альфа-коэффициенты обеспечивают адаптацию к трендам и асимметричную коррекцию рисков

2. **Принятие решений**:
   - Модуль decision определяет необходимое количество реплик на основе прогноза
   - Учитываются ограничения шагов масштабирования и периоды cooldown

3. **Распределение нагрузки**:
   - Kubernetes автоматически распределяет трафик между новыми репликами с помощью Service
   - LoadBalancer или Ingress контроллеры обеспечивают равномерное распределение запросов

4. **Адаптация к изменяющимся условиям**:
   - При увеличении нагрузки система создает новые поды
   - Новые экземпляры автоматически включаются в балансировку трафика
   - При уменьшении нагрузки старые поды постепенно удаляются

Этот подход позволяет системе эффективно балансировать нагрузку, предотвращая как перегрузки, так и недостаток ресурсов.
